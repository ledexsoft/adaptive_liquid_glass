# macOS compatibility review (2026-11-13)

## Scope and active paths

Reviewed the original package on macOS, without building or launching a native
example application. The adaptive macOS shell is Cupertino; most controls use
Flutter Cupertino or Material fallbacks. The currently reachable AppKit platform
view in the public adaptive wrappers is `MacosNativeBlurView`. The presence of
other Swift factories does **not** mean their native controls were exercised.

## Reproduced and corrected

- AdaptiveApp + AdaptiveScaffold could not host Material text fields, form fields,
  checkbox, switch, slider or date picker without consumer-added ancestors and
  localization delegates. The macOS shell now supplies a transparent Material
  surface, brightness-aware Material theme and default Material localization.
  Surfaces cover custom app-bar inputs as well as the page body; the body
  surface stays above Cupertino decoration so ink remains visible. Consumer
  delegates take precedence. Both imperative and router app forms are
  covered. The iOS app path is unchanged.
- AdaptiveToolbar's fallback used BottomAppBar, which demanded ScaffoldGeometry
  even inside CupertinoPageScaffold. macOS now uses a plain Material surface when
  no Material Scaffold exists, without introducing a nested Scaffold.
- A tabbed macOS scaffold dropped app bars whose only content was titleWidget or
  subtitle. Icon-only actions also dropped explicit semanticLabel.
- macOS secondary click did not open context menus.
- Removing an external search controller discarded the current editing value.
- AppKit blur creation could lose property changes while awaiting platform-view
  creation. It now reconciles the latest properties after creation.
- AppKit blur inverted regular/clear enum values. Its pre-26 fallback also
  converted absent/transparent tint into a black 25% overlay. Alpha is preserved
  and cleared tints remove the overlay. Native channel handlers are detached on
  view destruction.

## Automated coverage added

`adaptive_macos_integration_test.dart` tests the real AdaptiveApp + AdaptiveScaffold
composition, not a consumer-supplied MaterialApp/Scaffold workaround. Smoke tests
cover buttons, icon buttons, cards, list tiles, four chip types, expansion tiles,
tab views, fields, checkbox, switch, search, radio, slider/range, segmented
control, toolbar and tooltip. Interaction tests cover editing/controller
replacement/disposal, checkbox keyboard activation and disabled state, repeated
time-picker cancellation, date-picker cancellation, navigation push/pop with
editing state retained, forced dark theme, custom app-bar title/accessibility,
and the router variant.

`adaptive_macos_input_lifecycle_test.dart` covers secondary-click menu selection
and search controller ownership transfer with selection/composing state.

`adaptive_macos_blur_lifecycle_test.dart` mocks asynchronous platform creation and
checks the channel updates; a separate Swift source-contract assertion checks
style constants, alpha handling and cleanup. Source checks are **not** a native
rendering or memory-leak test.

## Limits

No native executable build, AppKit visual inspection, real VoiceOver session,
macOS 26/pre-26 device matrix, performance benchmark, or native memory-leak test
was performed. A full Flutter suite protects existing covered iOS/Android
behavior but does not establish exhaustive native-platform correctness. Remaining
native-only validation should target blur appearance, window resizing,
focus/keyboard behavior and VoiceOver on actual supported macOS versions.
